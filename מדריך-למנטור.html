Gov-Labs 2.0 · מדריך למנטור

המדריך למנטור לעבודה עם ה-Playbook

הפלייבוק מחזיק את המתודה ואת הגדרות הסוכנים, פעם אחת לכל המיזמים. המיזם שלך מחזיק את החומרים והתוצרים של הצוות. המדריך מסביר איך מחברים ביניהם, ב-Windows או ב-Mac, ובכל כלי AI: Claude Code, Gemini, Kiro ואחרים.

המחשב שלי:
הפקודות והנתיבים במדריך מתאימים את עצמם לבחירה.
1הכנת סביבת העבודהפעם אחת, כשעה 2הקמת מיזםפעם אחת לכל מיזם, כ-5 דקות 3עבודה שוטפתבכל מפגש עם הצוות

איך זה בנוי

הכול נמצא ב-repo אחד של המיזם. הסוכן רץ מתוכו: הוא קורא את המתודה מהעותק של הפלייבוק ואת החומרים מתיקיית היום, מתשאל את הצוות, וכותב את התוצר רק אחרי אישור.

קוראים בלבד

הפלייבוק, .playbook/

מפרט הסוכן, התהליך של היום, המתודה והטמפלט של התוצר. עותק של הפלייבוק, שנכנס ל-repo בהקמה ומתחדש בעדכון.

מי שמוריד (clone) את ה-repo מקבל הכול, כולל הפלייבוק, ולכן אין מה לחבר במחשב. הצוות לא צריך לדעת git: חומרים מעלים לתיקיית היום דרך האתר של GitHub (Add file ואז Upload files), או שהמנטור מעתיק אותם. את הסוכן מפעילים המנטור או מפעיל ה-AI של הצוות.

1הכנת סביבת העבודה

פעם אחת, לפני המיזם הראשון. אפשר לסמן כל שורה אחרי שסיימת.

רשימת התקנות

טרמינל ופקודות

את הפקודות מריצים בטרמינל. ב-VS Code וב-Kiro: בתפריט Terminal בוחרים New Terminal. ב-Windows בוחרים Git Bash בחץ הקטן ליד סימן הפלוס בחלון הטרמינל. ב-Mac הטרמינל הרגיל מתאים.

זהות git, פעם אחת (עם השם והמייל שלך):

git config --global user.name "השם שלך"
git config --global user.email "you@example.com"

העתקת הפלייבוק למחשב, פעם אחת:

mkdir -p /c/Dev
git clone https://github.com/Strauss-X-Labs/Gov-Labs-Playbook.git /c/Dev/Gov-Labs-Playbook
mkdir -p ~/Dev
git clone https://github.com/Strauss-X-Labs/Gov-Labs-Playbook.git ~/Dev/Gov-Labs-Playbook

לא צריך לעדכן את העותק הזה לפני כל הקמה: ההקמה מושכת תמיד את הגרסה העדכנית מ-GitHub. מספיק git pull מדי פעם.

בדיקה שהכל עובד

  1. פתח את תיקיית הפלייבוק בעורך (File ואז Open Folder), ואת כלי ה-AI בתוכה.
  2. בדוק שהכלי רואה את ההוראות. ב-Claude Code וב-Gemini CLI מקלידים /, ו-onboard-project צריך להופיע ברשימה. בכלים אחרים שואלים: "מה יש בתיקייה skills?", ובתשובה צריך להופיע onboard-project.
  3. לא עובד? עדכן את הפלייבוק (git pull) ופתח את הכלי מחדש. ראה גם תקלות נפוצות.

מהלך ההקמה

  1. פותחים את תיקיית הפלייבוק ומפעילים את ההקמה. ב-Claude Code או ב-Gemini CLI מקלידים /onboard-project. בכלים אחרים מדביקים את משפט הפתיחה. הסוכן שואל את שם ה-repo, ומאשר איתך את החשבון ואת הפלייבוק.
  2. משיכת הפלייבוק. הסוכן מוריד את הגרסה העדכנית של הפלייבוק מ-GitHub.
  3. בדיקות מקדימות. הסוכן בודק את זהות ה-git, ואם ה-repo כבר קיים, שיש לך הרשאה לכתוב בו.
  4. אישור. מוצגת טבלה של כל מה שייווצר. שום דבר לא נוצר לפני שכתבת "כן".
  5. ביצוע. הסוכן עושה ארבעה דברים:
    • פותח repo פרטי (או משתמש בקיים) ומעתיק אליו את תבנית המיזם.
    • יוצר תיקייה לכל יום בתוכנית, לפי הימים שבפלייבוק.
    • מעתיק את הפלייבוק ל-.playbook/.
    • שומר ודוחף את הכל ל-GitHub.
  6. דיווח. תקבל לינק ל-repo, ורשימה של מה שנשאר לך לעשות: לתת הרשאות ב-GitHub לחברי הצוות.

עבודה עם הסוכן

פותחים את תיקיית המיזם (לא את הפלייבוק), ומדברים בשפה חופשית על מה שקורה עכשיו. אין פקודה להרצת סוכן: הסוכן מזהה את היום ואת השלב, והתהליך של היום קובע איזה סוכן, באיזו משימה. לדוגמה:

אנחנו ביום 4, בוא נתחיל בבדיקת המוכנות ל-Lean Canvas.

ובהמשך היום: "הצוות סיים את קובייה 6", "סיימנו". בכלים בלי CLAUDE.md או GEMINI.md פותחים במשפט הפתיחה. לא ברור לסוכן איפה אתם — הוא שואל, לפי סדר היום. הרשימה המלאה נמצאת ב-טבלת הסוכנים בפלייבוק. סוכן חדש שנוסף לפלייבוק מגיע למיזם בעדכון הבא (/update-project).

מה קורה בהרצה:

  1. איתור. הסוכן מזהה את היום ואת השלב, מסקירת היום בפלייבוק.
  2. קריאת המתודה. התהליך קובע איזה סוכן ובאיזו משימה. הסוכן קורא מ-.playbook/ את התהליך, את קובץ הסוכן, את המתודות של המשימה ואת הטמפלט של התוצר.
  3. קריאת המיזם. הוא קורא את הקלטים שהתהליך מגדיר, כולל כל המופעים של תוצר (למשל מדריך ראיונות לכל פרסונה). כשהסוכן מוגדר לקרוא את כל מה שנמצא — הוא קורא הכול, בלי לשאול. הוא קורא מצגות, Word, PDF ותמונות.
  4. בדיקת קלטים. מוצגת טבלה של מה יש ומה חסר מתוך מה שהמפרט דורש. מה שחסר נשאל מהצוות, ולא מומצא.
  5. תשאול הצוות. שאלה אחת בכל פעם, לפי התסריט שבמפרט. הסוכן מאתגר, שואל "למה?", ושם לב לנורות האזהרה של התהליך.
  6. טיוטה. הסוכן מציג טיוטה במבנה של הטמפלט, כשהשערות מסומנות כהשערות. הצוות מתקן.
  7. כתיבה. רק אחרי אישור הצוות התוצר נכתב ל-תוצרים/. אם התוצר כבר קיים, הסוכן מציג מה משתנה ומעדכן, בלי לדרוס.
  8. תצוגה ותמונה, כשהסוכן מגדיר אותן. לדוגמה, בפרסונה נשמרים ליד קובץ ה-MD, באותו שם, גם תצוגה ויזואלית (.html) ותמונה. אם הכלי לא מחולל תמונות, הסוכן כותב פרומפט לכלי חיצוני, ואתה שומר את התמונה בשם שהוא נותן. אם הכלי מפרסם דפים לשיתוף, קישור השיתוף נרשם בראש קובץ ה-MD, ובכל עדכון הדף מתפרסם מחדש לאותו קישור.
  9. סיכום. מה נכתב, על מה זה מבוסס, ומה כדאי לבדוק בשטח. הסוכן גם מציע את הצעד הבא בתהליך.
מה הסוכן לא עושה

לא עורך את .playbook/, לא עורך ולא מוחק את החומרים של הצוות, לא ממציא מידע חסר, לא מחליט במקום הצוות, ולא שומר ב-GitHub בלי אישור.

תתי-צוותים במקביל

בתהליכים כמו הפרסונה, שני תתי-צוותים עובדים בו-זמנית. כל תת-צוות צריך סשן משלו: שני חלונות של כלי ה-AI על אותו מיזם, או שני מחשבים (ראה מחשב נוסף).

git add תוצרים/ 01-ימים/

git push מעלה ל-GitHub, ורק אז שאר הצוות רואה את התוצרים. מי שעובד ממחשב נוסף מושך את העדכונים עם git pull.

אחרי עדכון בפלייבוק

הפלייבוק מתעדכן כל הזמן: סוכנים חדשים, תיקונים במתודה, ימים חדשים. המיזם מחזיק עותק משלו ב-.playbook/, ולכן שום שינוי לא מגיע אליו לבד. זה בכוונה: מחזור שרץ לא משתנה באמצע, אלא כשאתה מחליט לעדכן.

השגרה, פעם בשבוע או לפני מפגש:

  1. פותחים את תיקיית המיזם ומקלידים /update-project (או משפט הפתיחה).
  2. קוראים את התוכנית. אם כתוב שהכול כבר מעודכן, אין מה לעשות. אחרת מאשרים, והסוכן שומר ומעלה ל-GitHub.
  3. פותחים סשן חדש בכלי ה-AI. כלים טוענים את ההוראות בתחילת סשן, ולכן העדכון נכנס לתוקף רק בסשן חדש.
