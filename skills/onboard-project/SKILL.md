# אכלוס מיזם חדש

אתה עוזר לצוות Gov-Labs 2.0 להקים את ה-repo שהקבוצה תעבוד בו לאורך כל התוכנית — ראה [README.md](../../README.md#שני-repos-לא-אחד), "שני repos, לא אחד". המבנה נגזר מהפלייבוק הזה, לא ממציאים אותו.

**גבול:** אתה מאכלס repo **אחר** (של המיזם). אתה **לא** עורך את הפלייבוק.

**שני מצבים:**
- **מיזם חדש** — repo חדש או ריק. שלבים 1–5 כרגיל.
- **עדכון מיזם קיים** — ה-repo כבר מכיל מיזם (יש בו `README.md` ו-`תוצרים/`), למשל כי התבנית השתנתה מאז שהוקם. אותם שלבים, אבל הבנייה דרך [upgrade.sh](upgrade.sh) — ראה "מצב עדכון" למטה.

## שלב 1 — קלט נדרש

אל תנחש. אם חסר — שאל:
1. **שם המיזם** (עברית, לתצוגה) — למשל "מיזם X של משרד הבריאות".
2. **GitHub** — אחד מהשניים:
   - **לינק לחשבון/ארגון** (`https://github.com/<owner>`) — ייפתח repo **חדש** שם. שאל גם **שם ל-repo** (אנגלית, kebab-case, למשל `pmo-work-plans`). לא ממציאים שם.
   - **לינק ל-repo קיים** (`https://github.com/<owner>/<name>`) — משתמשים בו.
3. **תיקיית השורש המקומית** — איפה במחשב ייווצר ה-clone, למשל `C:\Dev`. ה-clone נוצר ב-`<שורש>/<name>` (שם ה-repo). `<dir>` בהמשך = הנתיב הזה, בכתיב Git Bash (`C:\Dev` → `/c/Dev`).
4. **תיקייה ב-Google Drive** (לא חובה) — שם תיפתח תיקיית המיזם ובה תיקייה לכל יום. לא נתן — מדלגים על Drive. אחד מהשניים:
   - **נתיב מקומי** של Drive for desktop, למשל `G:\My Drive\...` או `G:\.shortcut-targets-by-id\...\<תיקייה>` — **עדיף**: בלי הגדרה ובלי התחברות, עם חשבון הגוגל שכבר מחובר במחשב. תיקייה ששותפה איתך מופיעה ב-`G:\` רק אחרי "Add shortcut to My Drive" בדפדפן.
   - **לינק** (`https://drive.google.com/drive/folders/...`) — דרך Google Drive API; דורש את ההגדרה החד-פעמית בסוף הקובץ.
5. **איפה יישמר החומר הגולמי** (מצגות, מסמכים, סיכומי דיונים, תמונות) — **החלטת המנטור**, לא שלך. שאל תמיד, גם אם נתן תיקיית Drive:
   - **`ידע/` ב-repo** — ברירת המחדל.
   - **Google Drive** — צריך **לינק** לתיקיית המיזם, כי ה-README נקרא ע"י אחרים ונתיב `G:\` לא עובד אצלם. אם יצרת את התיקייה מנתיב מקומי ואין לינק: בקש מהמנטור (ב-Drive: קליק ימני על תיקיית המיזם → Share → Copy link).

   התוצרים (פרסונה, Lean Canvas...) תמיד ב-`תוצרים/` ב-repo — זה לא חלק מההחלטה. ההחלטה נכתבת לסעיף "איפה החומר של המיזם" ב-README של ה-repo, ומשם כולם — אנשים וסוכנים — יודעים איפה לחפש.

## שלב 2 — מה ייכנס ל-repo

[scaffold.sh](scaffold.sh) בונה את זה — לא מעתיקים ביד:

| נתיב | מאיפה |
|---|---|
| `README.md`, `CLAUDE.md`, `.kiro/steering/מנטור.md`, `.gitignore`, `ידע/`, `תוצרים/` | [תבנית-מיזם/](../../תבנית-מיזם/), עם `[שם המיזם]` ו-`[מיקום החומר הגולמי]` מוחלפים |
| `.claude/` `.kiro/` `.agent/` `skills/run-agent/` | מצביע ל-[run-agent](../run-agent/SKILL.md) בפלייבוק — כך `/run-agent` זמין מתוך ה-repo של המיזם |
| `ימים/NN-<יום>/README.md` | תיקייה לכל יום ב-[01-ימים/](../../01-ימים/) (כל `NN-*`, בלי `_תבנית-יום`). ה-README מצביע לסקירה ולתהליכים של היום בפלייבוק |

רשימת הימים נקראת מ-`01-ימים/` בזמן הריצה — יום שנוסף לפלייבוק ייכנס אוטומטית. הסקריפט **לא דורס** קובץ שכבר קיים ביעד, ומדווח מה דילג.

**ב-Drive** (אם ניתנה תיקייה), [drive.sh](drive.sh) יוצר בתוך התיקייה: `<שם המיזם>/` ובתוכה `01-Unboxing/` … — תיקייה לכל יום, אותה רשימה. תיקייה שכבר קיימת באותו שם — משתמשים בה, לא משכפלים.

## שלב 3 — בדיקות מקדימות ואישור

לפני שמציגים משהו לאישור — שתי בדיקות שנכשלות אחרת רק ברגע ה-push:

1. **זהות git** — `git config user.name` ו-`git config user.email`. אם אחד ריק: שאל את המשתמש לשם ולמייל שלו. **לא** משתמשים בזהות של מישהו אחר (למשל מחבר של קומיטים קודמים). מגדירים רק ב-clone של המיזם (`git -C <dir> config user.name ...`), לא `--global`.
2. **GitHub:**
   - **repo חדש** — `gh repo view <owner>/<name>` צריך להיכשל (לא קיים). אם הוא **קיים** — עצור ושאל: להשתמש בקיים או לבחור שם אחר.
   - **repo קיים** — `git ls-remote` מוכיח רק קריאה. `gh api repos/<owner>/<name> --jq .permissions.push` צריך להחזיר `true`. אין `gh` — ציין שהרשאת הכתיבה תיבדק רק ב-push.
3. **Drive — נתיב מקומי:** התיקייה קיימת (`test -d`)? אין — בדוק ש-Drive for desktop פועל ושהתיקייה ב-My Drive או כקיצור דרך. תיקיית `<שם המיזם>` כבר קיימת בה — ציין שמשתמשים בה.
4. **Drive — לינק:** קיים `~/.gov-labs/google-token.json`? אם לא — צריך התחברות חד-פעמית:
   1. `bash skills/onboard-project/drive.sh auth-url` — תן למשתמש את הלינק. נכשל על "אין google-oauth-client.json" → עצור את חלק ה-Drive והפנה לסעיף "Google Drive — הגדרה חד-פעמית" למטה.
   2. המשתמש מאשר בדפדפן. הדפדפן יעבור ל-`http://localhost/?code=...` ויראה שגיאת "לא ניתן להתחבר" — **זה תקין**. בקש ממנו להעתיק את כל הכתובת משורת הכתובת.
   3. `bash skills/onboard-project/drive.sh auth-code "<הכתובת שהדביק>"`.

אחר כך — זו פעולה גלויה כלפי חוץ. **הצג למשתמש ובקש אישור:** שם המיזם, ה-repo (חדש ופרטי / קיים — ריק או עם תוכן), הנתיב המקומי `<dir>`, תיקיית ה-Drive (אם יש), איפה החומר הגולמי (`ידע/` / Drive + לינק), ורשימת הימים שייווצרו (`ls 01-ימים`).

## שלב 4 — clone, בנייה, push

כל הפקודות ב-bash (ב-Windows: Git Bash), מתוך שורש הפלייבוק. `<dir>` = `<שורש>/<name>` משלב 1.

**repo חדש** — קודם יוצרים אותו, **פרטי** (ציבורי רק באישור מפורש):

```bash
gh repo create <owner>/<name> --private --description "<שם המיזם> — Gov-Labs"
```

אין `gh` — כלי GitHub מחובר (`create_repository`, עם `organization` כשה-owner הוא ארגון, `private: true`). 403 / "not allowed to create" — אין הרשאה ליצור repos אצל ה-owner: דווח ועצור (ראה "כשל הרשאות"). אחר כך ממשיכים כמו repo ריק:

```bash
git clone https://github.com/<owner>/<name>.git <dir>
bash skills/onboard-project/scaffold.sh "<שם המיזם>" <dir> "<מיקום החומר הגולמי>"
# ידע/ → משמיטים את הפרמטר השלישי. Drive → "Google Drive: [<שם המיזם>](<לינק>)"
git -C <dir> add -A
git -C <dir> commit -m "אכלוס מיזם <שם המיזם> מ-Gov-Labs-Playbook"
git -C <dir> push origin HEAD
```

- **`<dir>` כבר קיים** — אם זה clone של אותו repo (`git -C <dir> remote get-url origin` תואם): `git -C <dir> pull` ומדלגים על ה-clone. אחרת — עצור ושאל; לא מוחקים ולא דורסים תיקייה קיימת.
- **repo ריק** (clone מזהיר "empty repository") — לפני ה-commit: `git -C <dir> checkout -b main`.
- **repo עם תוכן** — הסקריפט לא דורס. אם דילג על קבצים, הצג את הרשימה למשתמש לפני ה-push. אם ענף ברירת המחדל מוגן — push לענף `onboarding` ופתח PR.
- **נתן לינק ל-repo קיים, והוא לא קיים** — עצור ושאל אם ליצור אותו (כמו repo חדש, למעלה).
- **כשל הרשאות** (clone/push, למשל `403 Permission denied to <user>`) — דווח ועצור. לא מנסים עקיפה (חשבון אחר, טוקן אחר). אמור למשתמש מי המשתמש שנדחה, ושצריך הרשאת Write ל-repo מ-admin של הארגון. ה-clone עם הקומיט נשאר ב-`<dir>` — אחרי שההרשאה ניתנת מריצים רק `git -C <dir> push origin HEAD`.

**Drive** (אם ניתנה תיקייה) — אחרי ה-push. אותה פקודה לנתיב ולינק; הסקריפט מזהה לבד:

```bash
bash skills/onboard-project/drive.sh create "<נתיב מקומי או לינק>" "<שם המיזם>"
```

בנתיב מקומי — התיקיות מופיעות ב-Drive אחרי סנכרון (דקה-שתיים). הרשאת עריכה לתיקייה נדרשת בשתי הדרכים.

נכשל (הרשאה לתיקייה, התחברות שפגה) — ה-repo כבר מוכן; דווח על Drive בנפרד, אל תבטל את ה-repo. `File not found` על התיקייה = לחשבון הגוגל שהתחבר אין גישת עריכה אליה.

**חיבור לפלייבוק במחשב הזה** — אחרון, כדי ש-`/run-agent` יעבוד מתוך ה-repo של המיזם:

```bash
bash skills/run-agent/connect.sh <dir> ["<תיקיית המיזם ב-Drive for desktop>"]
```

הפרמטר השני — רק אם החומר הגולמי ב-Drive **וגם** יש נתיב מקומי: `<הנתיב שניתן בשלב 1>\<שם המיזם>` (התיקייה ש-drive.sh יצר). ניתן רק לינק — משמיטים; run-agent ישאל על הנתיב בהרצה הראשונה. הקבצים שנוצרים (`.gov-labs.local`, `.claude/settings.local.json`) מקומיים ולא עולים ל-git.

## מצב עדכון — מיזם קיים

מזהים אחרי ה-clone / pull: יש ב-`<dir>` גם `README.md` וגם `תוצרים/`. אז **לא** מריצים את `scaffold.sh` — מריצים את [upgrade.sh](upgrade.sh), שמשווה כל קובץ במיזם לכל הגרסאות של התבנית בהיסטוריה של הפלייבוק:

| הקובץ במיזם | מה קורה |
|---|---|
| חסר | נוסף |
| זהה לגרסה ישנה של התבנית (לא נערך ידנית) | מוחלף בגרסה העדכנית |
| שונה מכל גרסה (**נערך ידנית**) | **לא נוגעים.** מודפס diff |
| יצא מהתבנית ולא נערך (למשל `.gitkeep` ישן) | מוסר |
| יום חדש ב-`01-ימים/` | נוספת תיקייה |

1. **שם המיזם** — מהכותרת `# ...` ב-README של המיזם. אשר מול המשתמש; לא שואלים מחדש אם ברור.
2. **מיקום החומר הגולמי** — הסקריפט קורא אותו מה-README אם קיים. אין (README ישן) — שאל (קלט 5 בשלב 1).
3. **תוכנית:** `bash skills/onboard-project/upgrade.sh --dry-run <dir> "<שם המיזם>" ["<מיקום החומר הגולמי>"]` — לא משנה כלום. הצג את הפלט בשלב האישור (שלב 3).
4. **קבצים שנערכו ידנית** — הצג את ה-diff. הצע גרסה ממוזגת: הסעיפים החדשים מהתבנית **וגם** כל מה שהצוות הוסיף. כותבים אותה רק אחרי אישור מפורש, קובץ-קובץ.
5. **אחרי אישור:** אותה פקודה בלי `--dry-run`, ואז `connect.sh` (כמו במיזם חדש), קומיט `עדכון לתבנית העדכנית של הפלייבוק` ו-push.
6. **Drive** — `drive.sh create` בטוח להרצה חוזרת: תיקייה קיימת לא משוכפלת, ורק ימים חדשים נוספים.

## מה לא לעשות

- לא דוחפים בלי אישור מפורש על שם המיזם וה-repo.
- לא מוסיפים תיקיות או קבצים מעבר למה ש-scaffold.sh יוצר — ישות חדשה היא החלטת צוות (ראה [איך-תורמים.md](../../איך-תורמים.md), כלל 4). מבנה חדש נכנס לפלייבוק קודם (`תבנית-מיזם/` או `01-ימים/`), ומשם לכל המיזמים.
- לא כותבים תוכן מתודולוגי ב-repo החדש — הוא רק מצביע לפלייבוק.
- לא עושים force-push.
- לא מעלים ל-git את `google-oauth-client.json` או את `google-token.json` — הם נשארים ב-`~/.gov-labs/` של כל מנטור.

## Google Drive — הגדרה חד-פעמית (לארגון, לא לכל מנטור)

drive.sh מדבר עם Google Drive API ישירות, ולכן צריך OAuth client. מישהו עם הרשאות ב-Google Cloud של הארגון עושה פעם אחת:

1. [console.cloud.google.com](https://console.cloud.google.com) → פרויקט (קיים או חדש) → **APIs & Services → Library** → להפעיל **Google Drive API**.
2. **OAuth consent screen** — בארגון Google Workspace: `Internal`. אחרת: `External` במצב Testing, ולהוסיף את המנטורים כ-Test users.
3. **Credentials → Create credentials → OAuth client ID**, סוג **Desktop app** → Download JSON.
4. מעבירים את הקובץ למנטורים (לא דרך repo ציבורי). כל מנטור שומר אותו ב-`~/.gov-labs/google-oauth-client.json` (ב-Windows: `C:\Users\<שם>\.gov-labs\`).

אחר כך כל מנטור מתחבר פעם אחת (שלב 3 למעלה) — משם drive.sh רץ בלי התחברות נוספת.
