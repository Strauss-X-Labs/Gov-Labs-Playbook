# אכלוס מיזם חדש

אתה עוזר לצוות Gov-Labs 2.0 להקים את ה-repo שהקבוצה תעבוד בו לאורך כל התוכנית. ראה [README.md](../../README.md#שני-repos-לא-אחד), "שני repos, לא אחד". המבנה נגזר מהפלייבוק הזה, לא ממציאים אותו.

**הכול ב-repo של המיזם.** אין Google Drive, לא לקלט ולא לפלט:
- **חומר גולמי** (מסמכי Word, מצגות, סיכומי מפגש) — `01-ימים/NN-<יום>/` ב-repo של המיזם.
- **תוצרים** — `תוצרים/` ב-repo של המיזם.
- **הפלייבוק** — עותק ב-`.playbook/` בשורש ה-repo של המיזם. כל ההפניות של הסוכנים בתוך המיזם הן לנתיב היחסי הזה, ואף פעם לא לנתיב במחשב (כמו `C:\Dev\Gov-Labs-Playbook`).

**גבול:** אתה מאכלס repo **אחר**, של המיזם. אתה **לא** עורך את הפלייבוק.

**שני מצבים:**
- **מיזם חדש** — repo חדש או ריק. שלבים 1–5 כרגיל.
- **עדכון מיזם קיים** — ב-repo כבר יש `README.md` ו-`תוצרים/`. אותם שלבים, אבל הבנייה דרך `upgrade.sh`. ראה "מצב עדכון" למטה. מתוך repo של מיזם זה רץ כ-`/update-project`.

## שלב 1 — קלט

שואלים **רק** את זה. שלוש השאלות יחד, בהודעה אחת:

1. **שם ה-repo**, למשל `gov-labs-cycle10-climate-env-protect`. המבנה הוא `gov-labs-cycle<NN>-<נושא>-<קבוצה>`:
   - קידומת: `gov-labs`
   - מחזור: `cycle10`
   - הנושא של התוכנית, מילה אחת: `climate`
   - שם הקבוצה, יכול להכיל מקפים: `env-protect`

   בדיקה: `^gov-labs-cycle[0-9]+-[a-z0-9]+-[a-z0-9]+(-[a-z0-9]+)*$`. לא תואם — הצג את המבנה ושאל אם להמשיך בכל זאת או לתקן. לא חוסמים.
2. **חשבון GitHub** — ברירת המחדל `https://github.com/Strauss-X-Labs`. שאל: ברירת המחדל, או חשבון/ארגון אחר?
3. **הפלייבוק** — ברירת המחדל `https://github.com/Strauss-X-Labs/Gov-Labs-Playbook`. שאל: ברירת המחדל, או כתובת אחרת?

**נגזר, בלי לשאול** (מוצג בשלב האישור):
- **`<owner>/<name>`** — מהחשבון ומשם ה-repo.
- **שם המיזם** (לתצוגה, הכותרת ב-README): `Gov-Labs מחזור <NN> · <נושא> · <קבוצה>`, למשל `Gov-Labs מחזור 10 · climate · env-protect`. שם שלא תואם את המבנה — שם ה-repo כמו שהוא.
- **`<dir>`** — העותק המקומי: התיקייה **שמעל** תיקיית הפלייבוק שממנה אתה רץ, ועוד `<name>`. למשל: הפלייבוק ב-`C:\Dev\Gov-Labs-Playbook`, אז `C:\Dev\<name>`. ב-Git Bash ב-Windows `C:\Dev` נכתב `/c/Dev`. **רץ מתוך repo של מיזם** (`/update-project`): `<dir>` = שורש ה-repo הנוכחי. שם ה-repo והחשבון נלקחים מ-`git remote get-url origin`, והפלייבוק מ-`url=` ב-`.playbook/SOURCE`. מאשרים מול המשתמש, לא שואלים מחדש.

## שלב 2 — משיכת הפלייבוק העדכני

תמיד clone טרי מהכתובת משלב 1. לא משתמשים בעותק המקומי שממנו אתה רץ, כי הוא עלול להיות ישן או על ענף אחר. clone **מלא**, לא `--depth`, כי `upgrade.sh` משווה מול היסטוריית התבנית:

```bash
SRC="$(mktemp -d)/playbook"
git clone -q <כתובת הפלייבוק> "$SRC"
```

- **ה-SKILL.md שונה** — אם `$SRC/skills/onboard-project/SKILL.md` שונה מהקובץ שאתה קורא עכשיו, קרא את זה שב-`$SRC` והמשך לפיו.
- **מאיפה רצים** — כל הסקריפטים בהמשך רצים מ-`$SRC`, לא מהעותק המקומי. מה שנכנס למיזם (התבנית, הימים ו-`.playbook/`) הוא מהגרסה העדכנית.
- **בסוף** — `rm -rf "$(dirname "$SRC")"`.

## שלב 4 — בדיקות מקדימות ואישור

לפני שמציגים משהו לאישור — בדיקות שנכשלות אחרת רק ברגע ה-push:

1. **זהות git** — `git config user.name` ו-`git config user.email`. אם אחד ריק: שאל את המשתמש לשם ולמייל שלו. **לא** משתמשים בזהות של מישהו אחר (למשל מחבר של קומיטים קודמים). מגדירים רק ב-clone של המיזם (`git -C <dir> config user.name ...`), לא `--global`.
2. **GitHub:**
   - **ה-repo לא קיים** (`gh repo view <owner>/<name>` נכשל) — ייפתח repo חדש ופרטי.
   - **ה-repo קיים** — משתמשים בו. `gh api repos/<owner>/<name> --jq .permissions.push` צריך להחזיר `true`. אין `gh` — ציין שהרשאת הכתיבה תיבדק רק ב-push.
3. **`<dir>` כבר קיים** — אם זה clone של אותו repo (`git -C <dir> remote get-url origin` תואם): `git -C <dir> pull`, ומדלגים על ה-clone. אחרת — עצור ושאל. לא מוחקים ולא דורסים תיקייה קיימת.

זו פעולה גלויה כלפי חוץ, אז **מציגים למשתמש ומבקשים אישור** על:
- שם המיזם
- ה-repo: חדש ופרטי, או קיים (ריק או עם תוכן)
- הנתיב המקומי `<dir>`
- הפלייבוק: כתובת ו-commit (`git -C "$SRC" log -1 --format='%h %cs'`)
- רשימת הימים שייווצרו (`ls "$SRC/01-ימים"`)

## שלב 5 — clone, בנייה, push

כל הפקודות ב-bash. ב-Mac/Linux — `bash` רגיל. ב-Windows — Git Bash. אם הכלי מריץ PowerShell / cmd, או ש-`bash` מפנה ל-WSL: `& "C:\Program Files\Git\bin\bash.exe" <סקריפט> <פרמטרים>`.

**repo חדש** — קודם יוצרים אותו, **פרטי** (ציבורי רק באישור מפורש):

```bash
gh repo create <owner>/<name> --private --description "<שם המיזם>"
```

אין `gh` — כלי GitHub מחובר (`create_repository`, עם `organization` כשה-owner הוא ארגון, `private: true`). 403 / "not allowed to create" — אין הרשאה ליצור repos אצל ה-owner: דווח ועצור (ראה "כשל הרשאות"). אחר כך ממשיכים כמו repo ריק:

```bash
git clone https://github.com/<owner>/<name>.git <dir>
bash "$SRC/skills/onboard-project/scaffold.sh" "<שם המיזם>" <dir>
# לפני הקומיט: הצג למשתמש מה נוצר (git -C <dir> status --short) ושאל. ממשיכים רק באישור מפורש.
git -C <dir> add -A
git -C <dir> commit -m "אכלוס מיזם <שם המיזם> מ-Gov-Labs-Playbook (<commit של הפלייבוק>)"
git -C <dir> push origin HEAD
```

- **repo ריק** (clone מזהיר "empty repository") — לפני ה-commit: `git -C <dir> checkout -b main`.
- **repo עם תוכן** — אם יש בו `README.md` ו-`תוצרים/`, עוברים ל"מצב עדכון". אחרת, `scaffold.sh` לא דורס: אם דילג על קבצים, הצג את הרשימה למשתמש לפני ה-push. אם ענף ברירת המחדל מוגן — push לענף `onboarding` ופתח PR.
- **כשל הרשאות** (clone/push, למשל `403 Permission denied to <user>`) — דווח ועצור. לא מנסים עקיפה (חשבון אחר, טוקן אחר). אמור למשתמש מי המשתמש שנדחה, ושצריך הרשאת Write ל-repo מ-admin של הארגון. ה-clone עם הקומיט נשאר ב-`<dir>`; אחרי שההרשאה ניתנת מריצים רק `git -C <dir> push origin HEAD`.

## מצב עדכון — מיזם קיים

מזהים אחרי ה-clone / pull: ב-`<dir>` יש גם `README.md` וגם `תוצרים/`. אז **לא** מריצים את `scaffold.sh` אלא את [upgrade.sh](upgrade.sh):

| מה במיזם | מה קורה |
|---|---|
| `.playbook/` | מוחלף כולו בעותק העדכני. לא עורכים אותו ביד |
| קובץ תבנית חסר | נוסף |
| קובץ תבנית זהה לגרסה ישנה של התבנית (לא נערך ידנית) | מוחלף בגרסה העדכנית |
| קובץ תבנית שונה מכל גרסה (**נערך ידנית**) | **לא נוגעים.** מודפס diff |
| קובץ שיצא מהתבנית ולא נערך (למשל `ידע/.gitkeep`) | מוסר |
| יום חדש ב-`01-ימים/` של הפלייבוק | נוספת תיקייה |
| **מבנה ישן:** `ימים/<יום>/` | מועבר ל-`01-ימים/<יום>/`. הלינקים לפלייבוק ב-README של היום מופנים ל-`.playbook/` |
| **מבנה ישן:** קבצים ב-`ידע/` | **לא מוזזים**, רק מדווחים. רק הצוות יודע לאיזה יום כל קובץ שייך |
| **מבנה ישן:** `.gov-labs.local` | נמחק. זה קובץ מקומי, ואין בו צורך יותר |

1. **שם המיזם** — הסקריפט לוקח אותו מהכותרת `# ...` ב-README של המיזם. אשר מול המשתמש.
2. **תוכנית:** `bash "$SRC/skills/onboard-project/upgrade.sh" --dry-run <dir>` — לא משנה כלום. הצג את הפלט בשלב האישור (שלב 4).
3. **קבצים שנערכו ידנית** — הצג את ה-diff והצע גרסה ממוזגת: הסעיפים החדשים מהתבנית **וגם** כל מה שהצוות הוסיף. כותבים אותה רק אחרי אישור מפורש, קובץ-קובץ.
4. **קבצים ב-`ידע/`** — הצג את הרשימה ושאל לאיזה יום להעביר כל קובץ (`git -C <dir> mv`). אין תשובה — נשארים ב-`ידע/`.
5. **אחרי אישור:** אותה פקודה בלי `--dry-run`. אז הצג מה השתנה (`git -C <dir> status --short`) ושאל לפני הקומיט — רק באישור מפורש: קומיט `עדכון לפלייבוק <commit> ולתבנית העדכנית` ו-push.

## מה לא לעשות

- לא דוחפים בלי אישור מפורש על שם המיזם וה-repo.
- לא כותבים נתיב מקומי של הפלייבוק (`C:\...`, `/Users/...`) לשום קובץ במיזם. ההפניות הן תמיד `.playbook/...`.
- לא עורכים קבצים ב-`.playbook/` של מיזם. תיקון נכנס לפלייבוק עצמו ב-PR, ומגיע למיזם בעדכון.
- לא מוסיפים תיקיות או קבצים מעבר למה ש-`scaffold.sh` יוצר. ישות חדשה היא החלטת צוות (ראה [איך-תורמים.md](../../איך-תורמים.md), כלל 4). מבנה חדש נכנס לפלייבוק קודם (`תבנית-מיזם/` או `01-ימים/`), ומשם לכל המיזמים.
- לא כותבים תוכן מתודולוגי ב-repo של המיזם — רק מצביעים ל-`.playbook/`.
- לא עושים force-push.
