# נוהל-הפעלה-תוכניות-האצה-ופיתוח-טכנולוגי.docx

מנוהל הפעלה , תוכניות האצה ממשפחת Gov-Labs
מטרת המסמך לסייע להגדיר את תהליך העבודה בפיתוח מוצר בתוכניות Gov-Labs השונות
התקשרות ודרישות סף (Engagement)
פרופיל כוח האדם
יכולות Full Stack: שליטה בשרת Python או .NET, בניית UI ב-React והגדרת DB (PostgreSQL או חלופי) ללא תלות חיצונית.
One Dev Policy: מפתח קבוע מתחילה ועד סוף. החלפה גוררת חפיפה על חשבון הספק.
הנחת העבודה שלצורך הפיתוח מוקצים 250 שעות עבודה
הפיתוח מבוסס בינה מלאכותית (AI-Powered SDLC) . הטמעה מלאה של AI בכל שלבי ה-SDLC (אפיון ב-LLMs
מנהל מוצר שמלווה ב 30 אחוז משרה
צוות אחוד הכולל: מנטור טכנולוגי (ארכיטקט), מפתח, איש מוצר ספק ואיש מוצר משרד.
דגשים ליישום ה SDLC:
כחלק מתכולת הפיתוח יוקמו, כבר מתחילת הפיתוח, תהליכי CI/CD לבניה, בדיקה ופריסה אוטומטיים של כלל תכולת התוצר. במסגרת תהליכים אלו יכללו:
בדיקות אוטומטיות. אמורות, כאמור, להיות מפותחות ומוקמות כבר מתחילת הפיתוח ותורחבנה בשוטף, בהתאמה להתקדמות עם התכולות, זאת כדי שניתן יהיה לאבחן באופן מדויק את סטטוס הפיתוח בכל רגע נתון ולאפשר תהליך פיתוח איטרטיבי ויעיל. סוגי הבדיקות שימוכנו - בהתאמה להנחיות המופיעות בסעיפי ההמשך שבמסמך זה
יש להקים גם במסגרת תהליכי הפריסה את תוכנית הפריסה הראשית של התוצר המלא (שתבוסס על Terraform או כל טכנולוגית פריסה שקולה אחרת) עם תחילת הפיתוח ולהקפיד להרחיבה תוך כדי ההתקדמות עם התכולות והמשאבים שבהם נעשה שימוש במסגרת התוצר.
כבר מתחילת הפיתוח יש להקפיד על שימוש בתהליכי ה CI/CD שצוינו שלעיל לצורך ביצוע הבניה, הבדיקות והפריסה של כל פיתוח (Feature / Bug Fix / Full Version), בין אם מקומית, בעמדת המפתח ובין אם בסביבות הייעד השונות (אינטגרציה, בדיקות, קדם ייצור וכו'). התועלות:
להוכיח את השלמות והתקינות של תהליך ה SDLC האוטומטי של המיזם.
להנות מהאוטומציה כבר בשלב בפיתוח ועל ידי כך לשפר את הפרודוקטיביות וקצב ההתקדמות בתכולות
להקל על שלבי העברת המקל של תכולות הפיתוח לארגון.
חשוב לציין ! דגשים אלו רלוונטיים לכל מודל פיתוח: הן למודל הקלאסי והןלמודל פיתוח מוכוון בינה מלאכותית (AI-Driven SDLC).
שלב 2: היערכות והקמה (Setup)
3.1 תשתיות ומוכנות סביבה
תנאי סף: סביבת פיתוח (Cloud, Permissions, Boilerplate) באזור הנחיתה LZ של המשרד עם כל המשאבים הנדרשים.  הסביבה נדרשת לפני מפגש הארכיטקטורה. שהוא יום יעודי בכל תוכנית
Source Control: עבודה ב-Git המשרדי מהיום הראשון.
פריסת פרוייקט בסיס : המפתח פורס לסביבת המשרד פרוייקט הכולל את כל רכיבי התוכנה המקובלים.
שלב 3: תכנון וארכיטקטורה מהודקת (Tight Architecture)
4.1 תוצרי תכנון מנדטוריים (תנאי סף לתחילת פיתוח)
לפני התחלת המימוש הצוות מאשר את התוצרים הבאים (המותאמים לארכיטקטורת המוצר הספציפית):
Architecture Doc: * תרשים זרימה (Data Flow) בין ה-Frontend ל-Backend. (ראו ספריה לדוגמה)
הגדרה של רכיבי הניהול המרכזיים (לדוגמה: Orchestrator, Master Bot במערכות AI, או שירותי Core במערכות מידע) המנהלים את התהליך ומפעילים שירותי קצה.
מיפוי אינטגרציות (Integration Adapters) למערכות Legacy.
Journaling Concept: תכנון מבוסס "יומן אירועים" (Event Sourcing) המאפשר עקיבות מלאה אחר כל פעולה במערכת. (אחד מהערכים המוספים של שטראוס אסטרטגיה)
API First & Postman Collection: הגדרת Swagger וקולקציית Postman מלאה המשמשת כ-Single Source of Truth.
LLM Guardrails (במידה ורלוונטי): תוכנית לבקרת איכות תשובות ה-AI והערכתן (Evaluation).
שלב 4: ביצוע ושגרות עבודה (Execution)
שגרות מפגשים (מנדטורי)
סטטוס שבועי (צוות גרעיני - שעתיים): מעבר על ה-Backlog ב-Monday, דיון טכני/ארכיטקטוני עמוק, קבלת החלטות ועדכון משימות.
דמו דו-שבועי (צוות רחב): הדגמת "קוד עובד" (Live Demo) בלבד. ללא מצגות.
מחזור הפיתוח מחולק לשלושה ספרינטים (לא יותר מ 3 שבועות לספרינט), כאשר כל אחד מהם מייצר ערך מדיד וסביבה יציבה.
ספרינט 1: הוכחת ערך טכני ומוצרי (POV - Steel Thread)
מטרה: יצירת מסלול מקצה לקצה המוכיח שהארכיטקטורה והחיבור לענן עובדים.
תוצרים טכניים:
רכיבי התשתית מוכנים
ממשק UI מוכן לתפעול ראשוני
מנגנון קליטת נתונים (File Upload/Forms) ושמירה ראשונית בבסיס הנתונים.
מימוש APIs  (Contract) מאושר ב-Postman. כולל בדיקות אוטומטיות מול Data עסקי מסומלץ
ערך עסקי: חברי הקבוצה יכולים להבין את הכיוון המוצרי ויכולים להפעיל תרחישים עסקים ראשונים, גם עם הנתונים יהיו נתוני mock עסקים.
דגש AI SDLC: יצירת ה-Boilerplate , התבססות על API Spec first , תהליכי בדיקות אוטומטיות.
ספרינט 2: יציבות ויכולות Pilot (Sanity & Business Logic)
מטרה: הפיכת ה-POV למוצר פונקציונלי שניתן לבחון עם משתמשים.
תוצרים טכניים:
מימוש 80 אחוז מהתכולה העסקית
תיקוני באגים קריטים מהספרינט הראשון
תיעוד מלא של המערכת כולל תהליכי תחזוקה
שילוב משמעותי של מוביל פיתוח מהצוות (נציג המשרד)
בדיקות אינטגרציה (Integration Tests) המוודאות שהרכיבים מתקשרים ללא שגיאות.
ערך עסקי: הצוות יכול להתחיל לתרחש את בדיקת המשתמשים בנוסף יכול להתחיל לבצע בדיקות עסקיות על המוצר
ספרינט 3: מסירה והכנה להטמעה (Handover & Final Polish)
מטרה: סגירת קצוות טכניים והבטחת המשכיות עצמאית של המשרד.
תוצרים טכניים:
ליטוש UI/UX סופי בהתאם ל-Design System הממשלתי, או התכנון המקורי.
אופטימיזציה של שאילתות (Performance Tuning) וביצועי השרת.
בדיקות שפיות (Sanity) מלאות וסופיות בסביבת ה-Test המשרדית.
תיעוד טכני מלא בתוך הקוד ומסמכי ארכיטקטורה מעודכנים.
ערך עסקי: מוצר יציב, מהיר ומוכן לעלייה לייצור (Production) במשרד.
העברת ידע: סשנים של הדרכת צוות ה-IT המשרדי (כולל מעבר על הקוד והבדיקות).
שלב 5: מסירה והמשכיות (Handover)
חבילת תוצרים מורחבת
בסיום הפרויקט, הצוות הגרעיני יגיש חבילת "מוצר סגור" (Production Ready) הכוללת:
README & Technical Documentation:
מדריך הרצה (Getting Started): הוראות התקנה מקומיות (Docker/Local Dev) וסקריפטים לפריסה (Deployment) בענן המשרדי.
תיעוד ארכיטקטוני מעודכן: תרשימי Component Diagram ו-Sequence Diagram סופיים המשקפים את המימוש בפועל.
ניהול סביבות: קובץ הגדרות (Environment Variables) לדוגמה הכולל את כל הקונפיגורציות הנדרשות.
Automated Testing & Postman Collection:
Postman Collection: אוסף שאילתות מלא המכסה את כל ה-API Endpoints, כולל משתני סביבה (Environments) ובדיקות אימות אוטומטיות (Tests Script) המוודאות תקינות תשובה (Status 200, מבנה JSON תקין).
Test Suite: כלל בדיקות ה-Unit וה-Integration שפותחו, עם דוח כיסוי קוד (Code Coverage).
Clean Code & Infrastructure Decoupling:
הפרדת שכבות: קוד המממש את עקרונות ה-Clean Architecture, כך שהלוגיקה העסקית אינה תלויה בספריות ענן ספציפיות.
Vendor Agnostic: מימוש ממשקים (Interfaces) עבור שירותי תשתית (כגון Storage, Database, LLM).
דוגמה: החלפת מודל AI (למשל מ-Gemini ל-Llama) או החלפת ספק ענן (GCP ל-AWS) צריכה להתבצע דרך שינוי קונפיגורציה או החלפת רכיב ה-Adapter בלבד, ללא נגיעה בליבת הקוד.
העברת מקל (The Handover Session)
ביצוע סשן Live Coding משותף שבו מפתחי המשרד מבצעים שינוי לוגי קטן במערכת תחת הנחיית הספק, להוכחת הבנת הקוד ויכולת התחזוקה העצמאית.
