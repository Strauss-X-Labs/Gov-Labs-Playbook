# MVP — התכולה המינימלית שנותנת ערך

> מקור: [0.2 methods_.docx](../../חומרי-מקור/מסמכים/אביבית/0.2%20methods_.docx) — תוכן ההרצאות של Gov-Labs, כפי שתועד ע"י אביבית.

## מהות

אנחנו לא בעולם מושלם — את המתודה אפשר להפעיל בכל שלב, גם אם מישהו מגיע עם רשימת תכולה מגובשת או כבר רץ עם מוצר קיים. כל שלב נגזר מהקודמים, ושלושת השלבים סוגרים את הפערים שנוצרים:

1. **מהי החוויה שנרצה ליצור, ואיך מתרגמים אותה לממשק?** — השאלה הכי משמעותית, הקו שמחבר בין האסטרטגיה המוצרית לממשק הוויזואלי.
2. **מהי התכולה המינימלית שתיתן ערך (MVP)?** — הגדרת הרכיבים ל-MVP.
3. **בנייה ותכנון המסכים** — ראה [בניית המסכים](בניית-המסכים.md).

## מהו MVP

המצרף הקטן ביותר של תכונות / פיצ'רים שיכולים לשמש כמוצר בפני עצמו ולתת את הערך הגבוה ביותר **לבעיה המרכזית** שהמיזם מנסה לפתור.

עקרון היסוד (Lean UX): נקודת המפתח היא הבעיה המרכזית — לא כל הבעיות. זה דורש להתמקד. לא פותרים את כל הבעיה במוצר הראשוני — **אבל זה לא חצי פיתוח.** מה שעולה, עולה שלם ושמיש ועומד כמוצר בפני עצמו (פחות טוב, אולי ידני) אבל מייצר את התוצאה. הלקוח לא צריך להרגיש שמשהו שבור.

```
NOT LIKE THIS:   גלגל ──► ציר גלגלים ──► חצי מכונית ──► מכונית שלמה
                 (לא שמיש בשום שלב, עד שהמוצר הסופי מוכן)

LIKE THIS:       קורקינט ──► אופניים ──► אופנוע ──► מכונית
                 (כל שלב הוא כלי תחבורה שלם ושמיש בפני עצמו)
```

בגישה הקלאסית לוקח הרבה זמן עד שמביאים מוצר שלם ויוצרים ערך. בגישה הרזה נותנים ערך בשלבים מוקדמים, בודקים את הרעיון במינימום סיכון, וחותכים משמעותית בעלויות ובזמן.

## שאלת MVP טובה

מתמקדת ב**הנחת יסוד קריטית, ספציפית ומדידה**. בוחנת את ההנחה שעליה נשען המיזם, ומתארת תוצאה / התנהגות רצויה — לא תחושות או מחשבות.

| שאלה | תקינה? |
|---|---|
| האם יש ביקוש אמיתי לפתרון שלנו? האם אנשים יקנו נעליים באינטרנט? | ✅ |
| האם אנשים ייכנסו לאפליקציה? האם אנשים יאהבו את המוצר? | ❌ לא ספציפי, לא מדיד |

## דוגמאות מהתעשייה

- **Zappos** — השאלה: "האם אנשים מוכנים לקנות נעליים אונליין?" (כשרק ספרים נקנו אונליין). ה-MVP: המייסד צילם נעליים בחנויות מקומיות ופרסם באתר. כשמישהו קנה — הלך לחנות, קנה, ושלח. לא ניתן להרחבה ולא רווחי — אבל דרך מצוינת לבדוק ביקוש בלי להשקיע.
- **Airbnb** — הבעיה: זמינות לינה בערים מרכזיות בזמן כנסים. ה-MVP: שני חברים בסן פרנסיסקו צילמו את הלופט שלהם, העלו לאתר פשוט, וקיבלו 3 אורחים משלמים. בדקו את הנכונות לשלם על לינה שאינה מלון.
- **Instagram** — הגרסה הראשונה (Burbn) הוכיחה שתכונה אחת מעניינת אנשים: שיתוף תמונות ותגובות. הרגו את כל השאר, נשארו עם שיתוף תמונות, ופיתחו על בסיס פידבק.
- **Pango** — האם אנשים יפעילו חניה בלחיצת כפתור?
- **דיווח הכנסה** — האם אנשים יקבלו ביטחון בממשק הדיגיטלי ולא יגיעו פיזית לפקיד המס?

## אזהרת מסע — MVP כתהליך מתמשך

> "If you're not embarrassed by the first version of your product, you've launched too late." — Reid Hoffman

בארגונים רגילים לקבל דברים מעוצבים ומושלמים. עקרון ה-MVP דורש לקבל גרסה ראשונית "לא מושלמת" — מספיק טובה כדי לצאת לשטח וללמוד ממנה.

```
┌─────────┐
│  Build  │  בניית המינימום הנדרש
└────┬────┘
     ▼
┌─────────┐
│ Measure │  בחינה תוך כדי תנועה — מה עובד ומה פחות
└────┬────┘
     ▼
┌─────────┐
│  Learn  │  למידה — שיפור / פיבוט
└────┬────┘
     └──────► Think big → start small → learn fast
```
