# IGDS — תוכנית עבודה: ספריית רכיבים מדויקת לכל מנוע AI

> ⚠️ **הוחלפה** על ידי `PLAN-IGDS-CODE-LIBRARY-v2.md` (2026-11-11). המסמך הזה נשמר לתיעוד. ניתוח הפערים בין התוכניות נמצא בסעיף 1 של v2.

> נכתב ב-2026-11-11. מבוסס על מה שקיים בפועל בפרויקט, ועל בדיקה חיה של קובץ Figma `FXkIGvCtnuZZDrMjiSm29r` (קריאה בלבד).

## 0. העיקרון

**לא מעתיקים רכיבים. מפנים אליהם.**

כל רכיב IGDS כבר קיים פעמיים, בשתי צורות רשמיות:

| איפה | מה זה | איך AI משתמש בו בלי לשנות אותו |
|---|---|---|
| קוד: `@igds/core-web` | 73 תגים (`<igds-button>`, `<igds-vertical-filter>`…). הספרייה עצמה מציירת את הרכיב | ה-AI כותב **רק את התג, עם attributes מתוך רשימה סגורה**. המראה, המצבים, הנגישות וה-RTL מגיעים מהחבילה, לא מה-AI |
| Figma: הספרייה הקנונית | 707 component sets ו-6,622 וריאנטים | ה-AI **מציב instance של רכיב הספרייה** ובוחר ערכי וריאנט מתוך רשימה סגורה. הוא לא מצייר שכבות |

התהליך הנוכחי ("link to selection" לכל רכיב, ו-Kiro בונה אותו מחדש ב-HTML/CSS) הוא בדיוק הדבר שצריך להפסיק. כל בנייה מחדש היא העתקה, ולכן תמיד תהיה לא מדויקת.

## 1. למה זה לא מדויק היום — שורש הבעיה (נבדק)

1. **אין Code Connect בקובץ.**
   - בדיקה: `get_code_connect_map` על `Vertical Filter Item` (`3168:1715`) מחזיר `{}`.
   - לכן כשמעבירים ל-AI קישור לרכיב, Figma MCP מחזיר **שחזור של השכבות** (מסגרות, צבעים, טקסט) ולא את הקוד הרשמי.
   - ה-AI בונה look-alike, והמעצבות מתקנות ידנית.
2. **שמות הווריאנטים ב-Figma לא תואמים ל-API של הקוד.** במיפוי האוטומטי הקיים (`figma/figma-mapping.generated.json`):
   - רק 15 מאפייני וריאנט מיושרים.
   - 33 עם ערכים שונים.
   - 34 בלי מאפיין מקביל.
   - 18 בוליאניים בלי מקביל.
   - 74 שאינם props בכלל (מצב hover, RTL וכו').
3. **דוגמה מהקישור ששלחת: עמוד Filter (`2963:23162`).**
   - ל-`Vertical Filter Item` יש 24 וריאנטים: `State`, `RTL`, `Second Level`, `Expanded`.
   - ב-`<igds-vertical-filter>` אין attributes בכלל. הרמה, המצב הפתוח וה-disabled נקבעים בנתונים (JS property), וחלק מהמצבים הם runtime בלבד.
   - בלי טבלת תרגום, אין ל-AI דרך נכונה לבטא "Expanded=True". לכן הוא ממציא.

**המסקנה:** הפתרון הוא לא prompt טוב יותר. צריך:
- **(א)** חוזה תרגום מכני ומלא בין כל וריאנט ב-Figma לבין קוד.
- **(ב)** חיבור החוזה ל-Figma MCP עצמו.
- **(ג)** שערי בדיקה שלא תלויים במודל.

## 3. שלבי עבודה

כל שלב כולל תוצר, אוטומציה ותנאי סיום מדיד. אין שלב שעובר רכיב אחר רכיב ידנית. החלטות אנושיות מרוכזות ברשימת חריגים אחת לכל שלב.

### שלב 1 — חוזה הרכיבים (IGDS Component Contract)

**תוצר:** `igds-registry/contract/igds-contract.generated.json`, ודוח `contract/CONTRACT-REVIEW.generated.md`.

**לכל component set ציבורי ב-Figma** (126 ב-web, ובהמשך גם 36 במובייל), החוזה כולל:

**מזהי Figma:**
- `componentKey`: למיקום instance אמיתי.
- `nodeId` וקישור.

**כל מאפייני הווריאנט וה-component properties:**
- סוגי המאפיינים: VARIANT, BOOLEAN, TEXT, INSTANCE_SWAP.
- כל הערכים המותרים.

**תרגום לקוד, לכל ערך** (סוג אחד בלבד מתוך הרשימה):

| סיווג | משמעות |
|---|---|
| `attribute` | שם attribute וערך מדויקים |
| `property` | JS property ומבנה הנתונים, נגזר מטיפוסי ה-TypeScript שכבר מחולצים |
| `slot` | שם slot |
| `runtime-state` | hover, pressed, focus. **לא נכתבים בקוד** |
| `direction` | RTL ← `dir` |
| `GAP` | אין מקבילה בקוד. ה-AI חייב לדווח פער ולא לבנות |

**פרטי הקוד:** תג, אופן טעינה (`import`) ואירועים.

**דגלי זמינות:**
- `figma-only`: שתי קבוצות:
  - 41 sets ציבוריים ללא התאמה אוטומטית, למשל Date Range, Time Picker, Signature, Phone Number Input, Composer AI ורשתות חברתיות. חלקם יתבררו כווריאנט של תג קיים: Text Area הוא `igds-input type="textarea"`, ו-Loaders עשויים להיות `igds-loader`.
  - 6 sets ש-Figma עצמו מסמן "קוד לא קיים עדיין", גם אם המיפוי האוטומטי שייך אותם לתג כללי: Split Button, Floating Button, Chat Input, Kpi Cards, Mega Menu, Scroll.
- `code-only`: 33 תגים, בעיקר תת-רכיבים.

**קישור לכרטיס ההנחיות** משכבת הידע: מתי להשתמש, מתי להימנע.

**אוטומציה:**
- הרחבת `build-figma-mapping.mjs` הקיים:
  - הוספת `componentPropertyDefinitions` ו-`key` ל-snapshot (סקריפט `use_figma` אחד, באצוות).
  - גזירת מיפוי ערך-לערך משלושה מקורות: union types של TS, ערכי ברירת מחדל, ובדיקת runtime.
- תרגום מבני (למשל `Second Level` ו-`Expanded` במסנן ← צורת הנתונים ב-property) נגזר מטיפוסי ה-TS. כשהגזירה לא חד-משמעית, הערך נרשם כ-`needs-decision`.

**החלטות אנושיות:**
- רק פריטי `needs-decision` ו-`GAP`, ברשימה אחת.
- ההכרעה נרשמת בקובץ overrides אחד (כבר קיים: `figma/figma-mapping.overrides.json`).
- לפי המצב היום: 36 התאמות ברמת medium או needs-review, ועוד ערכים בודדים.

**תנאי סיום:**
- [ ] לכל set ציבורי יש רשומה. מספר הווריאנטים בחוזה שווה למספר ב-Figma (2,876 ב-web).
- [ ] 0 ערכים בסטטוס "לא מסווג". כל ערך הוא attribute, property, slot, runtime-state, direction או GAP.
- [ ] כל `attribute` שבחוזה עובר את `igds:lint`, ולכן קיים בקוד בפועל.

### שלב 2 — Code Connect אוטומטי (המפתח ל-"link to selection" מדויק)

**מה זה נותן:**
- כשמשתמש או AI מבקשים את `get_design_context` על מסך או רכיב, Figma MCP מחזיר לכל instance את **הקוד הרשמי המדויק**, למשל `<igds-vertical-filter …>`, במקום שחזור שכבות.
- זה עובד בכל לקוח MCP: Claude Code, Cursor, Kiro, Copilot ועוד.
- לא צריך קבצים מקומיים ולא שרת MCP חדש.

**נבדק:**
- החשבון שלך הוא Full seat בארגון Enterprise (Ministry of Cyber and National Digital Matters). Code Connect זמין בתוכנית הזו.
- כרגע אין בקובץ אף מיפוי.

**אוטומציה:**
- **יצירת קבצים:** קבצי Code Connect (`*.figma.ts`, parser ל-HTML/web components) **נוצרים אוטומטית מהחוזה**. אין כתיבה ידנית.
  - כל מאפיין Figma ממופה ל-attribute או לערך.
  - `runtime-state` לא מופיע בפלט.
- **רכיבי `figma-only`:** ממופים ל-snippet פער מפורש, למשל `<!-- IGDS-GAP: Split Button — אין רכיב קוד. ראו IGDS-RULES §8 -->`. כך ה-AI מקבל הוראה לעצור ולא ממציא.
- **בדיקה לפני פרסום:** `figma connect parse` ו-validate.
- **פיילוט:** Button, Input Field, Vertical Filter.
- **פרסום מלא:** `figma connect publish`, עם `FIGMA_ACCESS_TOKEN` מהסביבה בלבד (לא נשמר בקבצים).

**נדרש אישור:**
- הפרסום מוסיף metadata של Code Connect לרכיבים בקובץ הקנוני.
- הוא לא משנה עיצוב, וריאנטים או שכבות.
- עדיין, זו פעולה על הספרייה הרשמית, ולכן צריך אישור של בעלי ה-DS. ראו החלטות בסעיף 5.

**לאמת בפיילוט:** תמיכת Code Connect ב-HTML/web components (Lit) בגרסה הנוכחית. אם התמיכה לא מספיקה, החלופה היא מיפוי בסיסי דרך כלי ה-MCP (`send_code_connect_mappings`), כלומר שם רכיב ומקור בלבד, בתוספת החוזה כקובץ.

**תנאי סיום:**
- [ ] `get_code_connect_map` מחזיר מיפוי ל-100% מה-sets הממופים בחוזה.
- [ ] `get_design_context` על עמוד Filter, ועל 3 מסכי דוגמה מהקובץ, מחזיר רק תגי `igds-*` עם attributes שעוברים lint, וסימוני `IGDS-GAP` במקומות הצפויים.

### שלב 3 — הוכחת דיוק: בדיקת התאמה חזותית Figma ↔ קוד

**מטרה:** להוכיח, ולא רק להבטיח, שכל וריאנט נראה בקוד כמו ב-Figma.

**אוטומציה:**
- **רינדור הקוד:** כל וריאנט ממופה מרונדר ב-Edge headless (כבר קיים ב-`verify-runtime.mjs`), עם ה-attributes מהחוזה.
- **רינדור Figma:** אותו וריאנט מרונדר מ-Figma דרך REST images API, בבקשות מרוכזות של מאות צמתים בקריאה, עם טוקן מהסביבה.
- **השוואה:** פיקסלים, וגם גודל ו-bounding box.
- **סיווג:** זהה / הבדל קל / שונה / לא ניתן לרינדור.

**פרשנות:**
- הבדל בשלב הזה הוא פער בין הספרייה (`@igds/core-web`) לבין Figma. הוא מדווח לצוות IGDS. **ה-AI לא "מתקן" אותו.** למשל radius-xs: ‏4 ב-Figma מול 2px בקוד, פער שכבר נמצא.
- מצבי `runtime-state` נבדקים בהדמיה: hover דרך CDP, ו-focus דרך `.focus()`.

**תנאי סיום:**
- [ ] דוח התאמה לכל הווריאנטים הממופים, כולל צילומי השוואה לכל ממצא.

### שלב 4 — שערים שלא תלויים במודל ("ה-AI לא ישנה על דעת עצמו")

הוראות לבדן לא מבטיחות כלום. ההבטחה היא שהפלט **לא עובר** בדיקה אם שונה.

**קוד** (הרחבה של `igds:lint` הקיים, שכבר בודק תגים, attributes, ערכים, slots, events וטוקנים):

| כלל חדש | מה הוא תופס |
|---|---|
| `E-NATIVE-SUBSTITUTE` | `<button>`, `<input>`, `<select>`, `<dialog>` וכו' בקובץ UI, כשקיים רכיב IGDS מקביל |
| `E-STYLE-OVERRIDE` | CSS שמשנה מראה של `igds-*`, כמו `::part` או צבע, רדיוס וגופן על התג |
| `E-STATE-AS-ATTR` | כתיבת מצב runtime כ-attribute, למשל `state="hover"` |
| `E-GAP-IGNORED` | שימוש ברכיב `figma-only` בלי סימון `IGDS-GAP` |

**Figma** (סקריפט `design-lint` חדש, דרך `use_figma`, קריאה בלבד):
- כל אלמנט UI בפריים התוצר הוא instance של רכיב מהספרייה הקנונית, לפי `componentKey` שבחוזה.
- אין instances מנותקים (detached).
- ערכי הווריאנטים מתוך החוזה.
- אין דריסות צבע או גופן מחוץ ל-variables.
- מסגרות פריסה מותרות, ומשתמשות רק במשתני מרווח.

**תנאי סיום:**
- [ ] כל כלל מכוסה ב-fixture טוב וב-fixture רע ב-`tests/`.
- [ ] `design-lint` מזהה בפריים בדיקה רכיב מנותק ומלבן שמחקה כפתור.

## 4. מה אפשר להבטיח ומה לא — בכנות

**מובטח:**
- **בקוד:** הרכיבים עצמם מצוירים על ידי החבילה הרשמית. ה-AI לא יכול לשנות אותם בלי להיכשל ב-lint.
- **ב-Figma:** תוצר שעובר `design-lint` בנוי רק מ-instances של הספרייה.

**לא מובטח:**
- **הרכבה ופריסה:** איזה רכיב מתאים לצורך, ומה הסדר במסך, הם עדיין בחירה של ה-AI. כרטיסי ההנחיות מכוונים את הבחירה, אבל לא אוכפים אותה.

**לא אפשרי עד שצוות IGDS יממש:**
- **רכיבי `figma-only`:** לא יכולים להופיע במדויק בקוד, וה-AI יחזיר IGDS-GAP. המספר הסופי ייקבע בשלב 1. נקודת המוצא היא עד 41 sets ללא התאמה, ועוד 6 ש-Figma מסמן "קוד לא קיים".
  - דוגמאות מ-41 ה-sets: Date Range, Time Picker, Signature, Composer AI.
  - ה-6 ש-Figma מסמן: Split Button, Floating Button, Chat Input, Kpi Cards, Mega Menu, Scroll.
- **פערים חזותיים בין הקוד ל-Figma:** בשלב 3 יימדדו ויועברו. עד שיתוקנו, הקוד קובע.

**React ו-Angular:** לא אומתו (אין `NPM_TOKEN`). התוכנית מכסה web components. הרחבה לשתי הספריות היא אותה שרשרת, עם parser אחר של Code Connect.

1. **מסלול ראשון:**
   - **המלצה:** קוד (web components) קודם. הדיוק מובטח שם על ידי החבילה, ו-Code Connect פותר ישירות את בעיית "link to selection".
   - **אחר כך:** מסלול Figma, כלומר עיצוב מסכים מ-instances.
2. **אישור לפרסם Code Connect בקובץ הקנוני.** זו metadata בלבד, בלי שינוי עיצובי, ובאישור בעלי ה-DS. בלי האישור, ערוץ ה-MCP עובד רק עם החוזה כקובץ, וזה פחות אוטומטי למשתמשים.
3. **טוקן Figma** עם הרשאות `file_content:read` ו-`code_connect:write`, כמשתנה סביבה בלבד.
4. **מי מכריע ברשימת החריגים** של שלב 1 (`needs-decision`): נציג UX ונציג פיתוח, פעם אחת, ברשימה מרוכזת.
